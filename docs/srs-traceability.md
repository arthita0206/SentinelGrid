## Documented Project Deviations

No deviation below is labeled "approved" — no formal approval record exists in the repository for any of them. Each is labeled **Documented Project Deviation**.

### 1. Kinesis → SQS substitution (`kinesis_to_sqs`)

- **Original expectation:** SRS FR-3.1 — IoT Core → Amazon Kinesis Data Stream.
- **Implemented alternative:** IoT Core → Amazon SQS (Standard) → SQS Consumer Lambda → Anomaly Detector Lambda.
- **Reason:** Kinesis deployment (Step 24) was rejected by AWS with `SubscriptionRequiredException` — this account is not subscribed to Kinesis at all. Independently re-confirmed in Step 49 via the orphaned Kinesis CloudFormation stack's live `ListStreams` call returning the identical error.
- **Impact:** FR-3.1 not literally satisfied; FR-3.2's retention default differs (4 days vs. 24 hours, and no retention at all on the durable DynamoDB history); FR-3.3's partitioning is data-level, not structural.
- **Affects functional behavior:** No — the end-to-end pipeline functions correctly on SQS (validated Steps 27, 38, 46).
- **Remains open:** Effectively permanent within this AWS account; would only be revisited with a different account.

### 2. Public frontend hosting blocked (`cloudfront_blocked`)

- **Original expectation:** A publicly accessible frontend via `infrastructure/frontend-hosting.yaml` (S3 + CloudFront + OAC).
- **Implemented alternative:** Frontend fully built and integrated with live data (Steps 39–44), validated only against a local dev server.
- **Reason:** AWS CloudFront returned an account-verification restriction, reproduced identically on two separate genuine deployment attempts (Step 45 and its resumption).
- **Impact:** Affects NFR-8 (public dashboard clarity/accessibility); does not affect backend correctness.
- **Affects functional behavior:** No.
- **Remains open:** Yes — pending AWS Support; not retried per explicit instruction in this and prior steps.

### 3. Root account remains the operating identity (`root_account_operations`)

- **Original expectation:** NFR-5's least-privilege principle implies routine operations should use a scoped, non-root identity.
- **Implemented alternative:** `SentinelGridOperatorRole` (Step 48) exists but has no working human-authentication path — root cannot assume roles (an AWS-wide restriction), no IAM Identity Center exists in this account, and creating an IAM user + access key was explicitly deferred to the account owner rather than performed automatically.
- **Reason:** Account-level constraint (no SSO) plus an AWS-wide restriction, plus a deliberate choice not to auto-create a long-lived credential without explicit approval.
- **Impact:** Affects NFR-5's operating-identity dimension only — the deployed service-execution roles remain least-privilege regardless (Step 47).
- **Affects functional behavior:** No.
- **Remains open:** Yes — pending an account-owner decision between the two paths documented in `docs/operator-identity.md` §7.

### 4. No configurable retry in the remediation workflow (`no_configurable_retry`) — RESOLVED in Step 51

- **Original expectation:** SRS FR-5.4 — retry failed recovery up to a configurable maximum, then escalate.
- **Originally implemented (Step 50 and earlier):** The deployed ASL (`step_functions/remediation_workflow.json`) escalated immediately on the first failure via a `Catch` block (`ErrorEquals: States.ALL`) on `ExecuteRemediation`/`VerifyRemediation` — no `Retry` block, no attempt counter, no configurable maximum existed anywhere in the ASL or application code.
- **Reason it existed:** Not documented anywhere as a deliberate trade-off — discovered during the Step 50 traceability pass, not previously flagged in any prior step's report. Likely an undocumented simplification from the Step 15–18 workflow design.
- **Resolution (Step 51):** A bounded, configurable retry loop (default 2 retries, bounds [0, 5], implemented via an ASL `Choice`+`Pass` counter — native `Retry.MaxAttempts` cannot take a runtime value) now retries `ExecuteRemediation` on any Execute/Verify failure before escalating. Deployed to the live state machine and validated both locally (24 dedicated tests) and live (Test A: success path unaffected, valid AWS-accepted ASL syntax confirmed). See `docs/step51_remediation_retry.md`.
- **Impact:** FR-5.4 is now genuinely implemented; not yet observed retrying a live failure (see that document's §11 for why).
- **Affects functional behavior:** Yes — a remediation attempt that fails now retries up to the configured budget before escalating, a materially different (and now SRS-conforming) operational behavior.
- **Remains open:** No longer open as a deviation. A narrower residual limitation remains (retry behavior validated locally but not live) — tracked in FR-5.4's own record, not as an architectural deviation.

## What SentinelGrid Demonstrably Implements Today

- A complete, live, end-to-end self-healing pipeline: simulated telemetry → AWS IoT Core → SQS → Lambda analysis → deterministic threshold-based anomaly detection → DynamoDB persistence → Step Functions-orchestrated remediation (Plan/Execute/Verify) → recovery-history persistence → CloudWatch metrics/dashboard/alarm → SNS escalation action.
- A working, live-tested public read-only Knowledge Query API (7 routes) backing an integrated (locally-served) frontend dashboard.
- A fault injection engine covering 4 fault types, exercised end-to-end for 2 of them (NODE_OVERLOAD, DATA_CORRUPTION) with correct classification and successful automatic remediation, plus a validated escalation path for HIGH-severity/unresolved cases.
- A demonstrated 500-node / 6,000-message ingestion burst with zero message loss, zero throttling, and correct per-node state persistence.
- Real, observed $0.00 AWS billing across a complete month and the current month-to-date, with low-cost configuration choices (on-demand DynamoDB, minimum Lambda memory, no idle reserved capacity) confirmed throughout.
- 14+ independently deployable CloudFormation stacks, each with its own deploy script, matching the SRS's independently-deployable-components intent.
- A fault-injection/simulator core with zero AWS SDK coupling at the import level, confirmed by direct inspection.

## What Remains Incomplete or Constrained

- **Kinesis is not deployable in this AWS account** (account-level subscription restriction); SQS is the practical, functionally-validated replacement, but FR-3.1/3.2/3.3 are not literally satisfied as originally specified.
- **Missing-heartbeat detection does not exist** — the deployed detector is stateless and cannot notice the absence of expected telemetry; SENSOR_DROPOUT and NETWORK_PARTITION cannot currently be detected end-to-end as a result.
- ~~No configurable retry exists in the remediation workflow~~ — **resolved in Step 51**: a bounded, configurable retry loop is now implemented and deployed (default 2 retries, bounds [0,5]); validated locally (24 tests) and live for the success path. Retry-of-an-actual-failure was not observed live (the deterministic simulation has no natural live failure trigger) — see `docs/step51_remediation_retry.md`.
- **Performance requirements (NFR-1, NFR-2) are not statistically demonstrated** — both rest on a single n=10 sample; NFR-1's raw result (90%) is below its own 95% target.
- **Detection accuracy and false-positive rate are not computed as ongoing metrics** anywhere in the system, and the one available ground-truth sample (Step 46, n=4) is a functional check, not a statistical figure.
- **MTTR is not computed as an explicit aggregate metric** — the closest proxy (RecoveryLatency) is deliberately not equated with it.
- **The Knowledge Query API is public and unauthenticated**, and has no request throttling — a documented, unresolved security/cost exposure (Step 47/49).
- **The AWS root account remains the operating identity** for this project — a dedicated least-privilege role exists (Step 48) but has no working non-root authentication path yet.
- **The frontend is not publicly hosted** — CloudFront remains blocked by an account-verification restriction, reproduced twice.
- **CloudWatch Lambda log retention is unbounded ("Never Expire")** and **the S3 deployment bucket has no version-lifecycle rule** — both currently negligible in size but structurally unbounded (Step 49).
- **NFR-4 ("no history loss")** reflects zero observed loss in specific tested workloads, not a permanent guarantee — no DynamoDB table has Point-in-Time Recovery or deletion protection enabled.
