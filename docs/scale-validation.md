# SentinelGrid Scalability Validation (Step 37)

## 1. Objective

Perform a controlled scalability validation of SentinelGrid toward SRS
NFR-3 (500 virtual nodes) — establishing evidence that the deployed AWS
pipeline can process telemetry generated by 500 virtual nodes without
unacceptable loss, duplication, backlog growth, or system failure. This
is NOT a claim that "the simulator started 500 nodes" — it is evidence
about what the real, deployed AWS pipeline actually did with the
resulting load.

## 2. SRS requirement being evaluated

**NFR-3**: The system should support 500 virtual nodes. Step 36 already
established NFR-1/NFR-2 baselines separately (n=10, both NOT
statistically demonstrated) — Step 37 does not re-litigate those, and
does not claim NFR-1/NFR-2 compliance from this step's evidence either
(see §9).

## 3. Phase A findings — current simulator/publisher (before any change)

- **Node count**: fully configurable via `config["power"|"water"|"traffic"]["num_nodes"]`
  — no hardcoded cap. Default (`config/simulation_config.yaml`) is 20/20/20 = 60.
- **Telemetry frequency**: `config["telemetry"]["interval_seconds"]`, default 5s.
- **Generation is sequential, in-process** (`CitySimulator.generate_all_telemetry()`
  loops over `self.nodes`) — fast (pure Python, no I/O), not a bottleneck
  at any tested scale.
- **Publishing was ALSO sequential** (`CitySimulator.run()`'s per-tick loop
  calls `self.publisher.publish(telemetry)` once per node, one at a
  time) — measured empirically at **~40-90ms per `AwsIotPublisher.publish()`
  call** (mean 50.7ms over 20 sequential live calls). At 500 nodes, a
  sequential loop would take **~25 seconds per tick** — far exceeding a
  5-second interval. **This is exactly why Step 37 needed new
  capability** (see §5, `ConcurrentPublisher`) rather than simply
  reconfiguring node counts.
- **`CitySimulator.run(max_ticks=N)`** already existed — bounded-duration
  runs were already supported; no change was needed for that.
- **AWS IoT publish quota**: confirmed via `service-quotas` — 20,000
  publish requests/second/account (far above any rate this test could
  produce) — the client side (this project's own simulator), not AWS
  IoT, was the actual constraint.
- **Fault injection**: already fully controllable — `fault_injection.enabled: false`
  is the existing default, and `FaultInjectionEngine` already accepts a
  `random_seed` for determinism. No change needed.
- **Determinism**: `PowerNode`/`WaterNode`/`TrafficNode` read values from
  the global `random` module directly (not individually seeded) — calling
  `random.seed(N)` before construction is sufficient for deterministic
  local tests; no production code change was needed for this either.

## 9. Bottleneck finding — AWS account Lambda concurrency limit

**`aws lambda get-account-settings` reports this account's
`ConcurrentExecutions` (and `UnreservedConcurrentExecutions`) limit as
just `10`** — not AWS's typical default of 1,000. Neither
`SentinelGridSqsTelemetryConsumer` nor `SentinelGridAnomalyDetector` has
any reserved concurrency configured (`get-function-concurrency` returned
empty for both) — both draw from this same 10-execution account-wide
pool, alongside every other Lambda in the account.

At 500 nodes / 5s (~100 msg/s), SQS's event-source-mapping poller scales
up pollers and concurrent consumer invocations well beyond 10 to keep up
— each hitting the account ceiling and being throttled
(`TooManyRequestsException`, reported as CloudWatch `Throttles`, not
`Errors`). AWS Lambda's own SQS integration automatically retries a
throttled poll/invoke rather than failing the message, which is exactly
what happened here: **1,455 + 3,582 = 5,037 throttle events occurred,
yet the final result was 6,000/6,000 (100%) successfully processed, 0
duplicates, 0 DLQ, 0 Errors.** The cost was NOT data loss — it was
**processing latency**: the full pipeline took ~11.5 minutes to fully
drain a load that published in under a minute, because most invocations
had to wait through repeated throttle/retry cycles rather than running
immediately.

**This is a genuine, previously-undiscovered constraint of the AWS
account this project runs in, not a flaw in SentinelGrid's own
architecture or code.** No optimization was applied — per Step 37's
explicit instructions, this is reported as a finding, not fixed. The
test remained reproducible and completed cleanly without it. The
concrete, actionable path (for a future step, explicitly NOT implemented
here) would be an AWS Service Quota increase request for Lambda
concurrent executions in this account/region — a manual, account-level
change outside this project's own IAM/CloudFormation control, which
would need to be requested by the account owner.

## 10. Optional fault sample (Phase G) — SKIPPED

Step 37's instructions are explicit: **"If the normal scale test already

**No fault sample was performed in Step 37.**

## 12. NFR-3 assessment

**PARTIALLY DEMONSTRATES NFR-3.**

**What was demonstrated**: the deployed, unmodified AWS pipeline
processed telemetry from all 500 virtual nodes across 12 ticks (6,000
events) with **100% completeness, 0 missing events, 0 duplicates, 0 DLQ
messages, and 0 Lambda errors**, using the real IoT → SQS → Lambda →
DynamoDB path with no bypass. This is meaningfully more than "500
simulator objects were created" — it is confirmed, end-to-end,
AWS-native evidence that the architecture correctly and completely
processes a 500-node telemetry load, verified independently through
DynamoDB (both the raw telemetry table AND the derived NodeState table,
proving the Analyzer itself — not just SQS ingestion — completed for
every node).

**What was NOT demonstrated**: sustained, low-latency THROUGHPUT at this
scale. The account's Lambda concurrency ceiling (10) caused heavy
throttling and a ~11.5-minute processing tail for a load that published
in under a minute — the system reached eventual completeness, not timely
completeness, under this specific account's current resource limits.
This step also did not test durations longer than ~1 minute of
publishing, node counts beyond 500, or concurrent/overlapping fault
scenarios at scale (§10).

**Conclusion**: NFR-3's core claim ("the system should support 500
virtual nodes") is supported for correctness/completeness under the
tested conditions, but not yet demonstrated for the account's currently
available Lambda concurrency headroom — that is an account-level
constraint discovered, not created, by this test, and is a legitimate,
actionable limitation to report rather than optimize around silently.

## 13. Limitations

- Single test run, ~1-minute bounded publish duration — no sustained
  multi-hour or repeated-run evidence.
- The account's Lambda concurrency limit (10) is itself an
  externally-imposed constraint this step did not (and was not asked to)
  attempt to change; a different AWS account/region with the standard
  1,000-execution default would very likely show a dramatically shorter
  drain time — this was not tested, since only this project's actual
  account was available.
- No fault sample was performed (§10) — no new NFR-1/NFR-2 evidence.
- `SentinelGridAnomalyDetector` Invocations (5,997) vs. the DynamoDB-confirmed
  6,000 processed telemetry items shows a small (3-item) discrepancy in
  the CloudWatch metric itself, most likely ordinary metric-reporting
  granularity/timing rather than a processing gap — the DynamoDB count is
  the authoritative completeness measure used for this report's
  conclusions, and it shows 6,000/6,000.
- Drain-time (~11.5 min) is bounded by this script's own 5-second polling
  granularity, not measured to sub-5-second precision.
- This step did not evaluate NFR-1/NFR-2 at all (§11) — those remain
  exactly as Step 36 left them (not restated here; see
  `docs/performance-validation.md`, unmodified by Step 37).

## 14. Recommended next step (Step 38 candidate — not implemented here)

1. Request an AWS Service Quota increase for Lambda concurrent executions
   in this account (from 10 toward the standard default, e.g. 1,000), then
   re-run this exact same bounded 500-node test to measure whether drain
   time drops dramatically — this would directly test whether §9's
   bottleneck is the sole cause of the processing tail.
2. If concurrency remains constrained, consider (with explicit approval
   before any change, per this project's standing rules) SQS event-source
   `MaximumConcurrency` tuning or a queue-depth-aware backpressure
   strategy suited to a low-concurrency account.
3. A combined NFR-1/NFR-2-at-scale test (a modest fault sample under the
   500-node load) once §9's throttling is either resolved or explicitly
   accepted as a known account constraint.
4. A longer-duration (not merely 60-second) sustained-load test, if
   NFR-3's real intent includes sustained operation, not just burst
   completeness.
